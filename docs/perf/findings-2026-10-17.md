# Stress test findings, 2026-10-17

Raw numbers: [stress-latest.md](stress-latest.md). Re-run them with
`tools/stress.sh [heavy|many|all] [--max=N]`.

Machine: Apple M1 Pro, Godot 4.7, native extension on, 2720×1710 render.
On this setup macOS paces frames at about 82 fps even with vsync off, so fps
only means something once it drops below that. Godot doesn't report GPU
timings on Metal here, so frame cost is CPU render time plus wall-clock fps.

## Summary

| Scenario | Comfortable | Where it tops out | What runs out first |
|---|---|---|---|
| Carved detail in one object | 100,000 cuts in a 2 m block | not reached | nothing; greedy meshing keeps it at ~60k quads |
| Worst-case noise (1 cm) | ~100,000 cells | ~1,000,000 cells | build time (3.3 s), RAM (480 MB), edit latency (76 ms) |
| Instances of one object | ~10,000 | ~100,000 | scene nodes, physics bodies, RAM (1.8 GB), edits (320 ms) |
| Unique small objects | ~1,000 | ~10,000 | draw calls (27k), load time (10 s), save time (3 s) |

## What the numbers say

1. **Detail is cheap.** Your sculpted block is the "carved" case. Even
   100,000 random cuts of 1–25 cm in a 2 m block mesh to only 60,000 quads in
   512 chunks. It renders at the frame cap, a 10 cm edit takes 1–5 ms, and it
   saves to 0.3 MB. Real carving keeps large flat areas that greedy meshing
   merges.

2. **Noise is the real ceiling for one object.** Random 50% fill at 1 cm
   gives ~1.4 quads per cell, which greedy meshing can't merge. One million
   cells means 1.4 M quads, 3.3 s to build, 480 MB of RAM and 76 ms per edit.
   Ten million cells (projected 14 M quads) was skipped. Real builds rarely
   look like this, but foliage, gravel or dithered paint at 1 cm would.

3. **Instances batch well, but each costs ~18 KB and 5 nodes.** 100,000
   instances of one object draw in about 10 calls (Godot batches identical
   meshes). But every rendered chunk of every instance is a MeshInstance3D +
   StaticBody3D + CollisionShape3D under 2 Node3Ds. At 100,000 instances
   that's 500,000 nodes, 1.8 GB of RAM, a 9.7 ms CPU frame, and 320 ms to
   apply one edit to the shared object.

4. **Unique objects cost draw calls.** Each unique object has its own mesh,
   so it can't batch: 10,000 unique crates need 27,000 draw calls (shadows
   included) and run at 35 fps. Each also stores a full 32 KB chunk for 10
   cells of data.

5. **Loading is slow for a silly reason.** `VoxelGrid.set_chunk` counts solid
   cells with a GDScript loop, about 1 ms per chunk. The 2 m block takes
   390–490 ms to load 0.3 MB, and 10,000 unique objects take 10 s.

## Suggested fixes, by payoff

1. **Load: count with `PackedByteArray.count(0)`** (a one-line native call).
   Expect loads 10–50× faster.
2. **Instances: stop making nodes per chunk per instance.** Draw instances
   with RenderingServer instances or MultiMesh, and create collision bodies
   only near the player. This is the change that lifts the 10k–100k instance
   ceiling.
3. **Unique small objects: smaller or sparse chunk storage** (e.g. 16³ or
   run-length chunks) so a 10-cell object doesn't hold 32 KB, and save
   objects into fewer files.
4. **Noise worst case: build collision lazily or on worker threads.** Collision
   and mesh upload, not the mesher, dominate the 3.3 s build. A simpler
   collision shape for dense chunks would also help.

## Bug found and fixed during the run

Per-instance shader parameters (used for deeper-object-wins rendering)
overflowed Godot's global instance-uniform buffer at about 10,000 chunks, and
the logged errors flooded the run. Rendering now uses one material per tree
depth, so meshes stay shared and the limit is gone.
